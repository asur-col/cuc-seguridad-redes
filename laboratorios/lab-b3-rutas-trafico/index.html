Laboratorio 1: Segmentación de Redes y Zero Trust

VirtualBox + OPNsense + Alpine Linux: tres zonas de servicio aisladas, una zona de administración con escritorio gráfico, NAT de salida, una aplicación web real con su base de datos protegida, y publicación controlada del servicio por NAT/PAT

Laboratorio B3 — Rutas y tráfico: ver el paquete salto a salto

Objetivo. Al terminar, puedes señalar en pantalla por dónde pasó una petición concreta: qué equipo la vio, con qué origen y destino, dónde el router la tradujo y qué regla la dejó pasar o la cortó. Y puedes provocar el tráfico tú mismo.

Parte A — La topología y sus tres redes

A.1 Preparar

  1. Copia el paquete del laboratorio y entra en él.
    asur-lab iniciar b3 && cp -r ~/labs/b3 ~/lab-b3 && cd ~/lab-b3
    Captura prevista para la prueba de la Fase 5: pantalla del paso «A.1 Preparar» con la salida real. Se guarda en imagenes/B3-01.png.
  • Comprueba que no hay contenedores anteriores con el mismo nombre.
    docker ps -a --filter name=lab-b3 --format "{{.Names}} {{.Status}}"

    • Salida esperada: la carpeta copiada y una lista vacía. Captura: los dos comandos.

    A.2 Levantar cliente, router, servidor interno y destino autorizado

    1. Revisa el docker-compose.yml del paquete: el router es el único con tres interfaces.
    # extracto de docker-compose.yml
  router:
    image: alpine:3.20
    container_name: lab-b3-router
    cap_add: [NET_ADMIN]
    sysctls:
      net.ipv4.ip_forward: 1
    networks:
      lan:     { ipv4_address: 10.20.0.1 }
      interna: { ipv4_address: 10.30.0.1 }
      externa: { ipv4_address: 10.40.0.1 }
  cliente:
    image: alpine:3.20
    container_name: lab-b3-cliente
    networks: { lan: { ipv4_address: 10.20.0.20 } }
  interno:
    image: nginx:1.27-alpine
    container_name: lab-b3-interno
    networks: { interna: { ipv4_address: 10.30.0.20 } }
  externo:
    image: nginx:1.27-alpine
    container_name: lab-b3-externo
    networks: { externa: { ipv4_address: 10.40.0.10 } }

    Las tres redes usan la puerta de enlace .254 porque el router ya ocupa la .1 en cada una.

    Captura prevista para la prueba de la Fase 5: pantalla del paso «A.2 Levantar cliente, router, servidor interno y destino autorizado» con la salida real. Se guarda en imagenes/B3-02.png.
    1. Levanta todo y espera unos segundos.
      docker compose -p b3 up -d
docker compose ps --format "{{.Name}} {{.State}}"
    2. Comprueba que el cliente solo tiene ruta al router.
      docker exec lab-b3-cliente ip route
    3. Comprueba que el router reenvía.
      docker exec lab-b3-router sysctl net.ipv4.ip_forward

    Salida esperada: cuatro servicios running; en el cliente default via 10.20.0.1; en el router net.ipv4.ip_forward = 1. Captura: las tres salidas.

    A.3 Las reglas que deciden

    1. Aplica las reglas del laboratorio con el script del paquete y muéstralas.
      docker exec lab-b3-router sh /reglas.sh
docker exec lab-b3-router iptables -t nat -L POSTROUTING -v -n
docker exec lab-b3-router iptables -L FORWARD -v -n

    Salida esperada: una regla MASQUERADE en la cadena de NAT con contador, y en FORWARD una regla ACCEPT hacia el servidor interno en su puerto, otra hacia el destino autorizado y un DROP al resto. Captura: las dos tablas con los contadores.

    Anota los contadores antes de generar tráfico. Si después no cambian, el paquete no pasó por esa regla y la conclusión no vale.

    Parte B — Provocar el tráfico y verlo

    B.1 Arrancar el visor

    1. Arranca el visor sobre los tres contenedores que importan.
      cd ~/lab-b3
python3 colector.py --contenedores lab-b3-cliente,lab-b3-router,lab-b3-interno --puerto 8099 > ~/visor.log 2>&1 &
      El visor queda en segundo plano y su salida va a ~/visor.log. Para detenerlo, pkill -f colector.py.
      Captura prevista para la prueba de la Fase 5: pantalla del paso «B.1 Arrancar el visor» con la salida real. Se guarda en imagenes/B3-03.png.
    2. Abre el visor en el navegador de la VM y deja la pestaña a la vista.

    Salida esperada: visor en http://0.0.0.0:8099 y la página con la topología y la tabla vacía. Captura: la página abierta antes de generar tráfico.

    B.2 Una petición al servidor interno

    1. Pulsa Generar tráfico al servidor interno en el visor y espera dos segundos.
    2. Comprueba en la tabla que hay tres saltos, uno por contenedor.
    3. Mira la marca NAT en el salto del router y compara el origen de antes y después.
    4. Vuelve a mirar el contador de MASQUERADE.
      docker exec lab-b3-router iptables -t nat -L POSTROUTING -v -n
    5. Sin ratón, el mismo trabajo desde la terminal.
      ./generar_trafico.sh
      Los botones del visor llaman a /api/generar. El paquete trae el mismo tráfico en generar_trafico.sh: hace los tres flujos (interno, salida y el que debe cortarse) y muestra los contadores del router.

    Salida esperada: tres saltos para el mismo flujo (cliente, router, interno); en el router el origen ya no es 10.20.0.20 sino 10.20.0.1; el contador de MASQUERADE mayor que antes. Captura: la fila con los tres saltos y la marca NAT, y el contador después.

    B.3 Una salida al destino autorizado

    1. Pulsa Generar salida a internet.
    2. Comprueba que este flujo tiene dos saltos y también marca NAT.
    3. Filtra por 80 en la caja de búsqueda.

    Salida esperada: dos saltos (cliente y router), marca NAT y, al filtrar por 80, solo ese flujo. Captura: la tabla filtrada.

    B.4 Lo que el firewall corta

    1. Intenta llegar al puerto cerrado del servidor interno.
      docker exec lab-b3-cliente wget -T 2 -O- http://10.30.0.20:22/ ; echo "salida=$?"
    2. Mira el visor: debe aparecer el intento con la marca de bloqueo.
    3. Confirma qué regla lo cortó.
      docker exec lab-b3-router iptables -L FORWARD -v -n | grep -E "DROP|REJECT"

    Salida esperada: el wget falla; en el visor el flujo aparece con bloqueado y el router responde con un ICMP de puerto inalcanzable; la regla que corta muestra su contador incrementado. Captura: el fallo, la fila marcada y la regla.

    Aquí está lo que se pide demostrar: no basta decir que el firewall bloquea; hay que enseñar el paquete que no llegó, la regla que lo cortó y el contador que lo confirma.

    Entregable y comprobación

    Entrega informe-b3.md con cuatro capturas y una frase por captura: (1) tabla con los tres saltos del flujo interno y la marca NAT; (2) contador de MASQUERADE antes y después; (3) tabla filtrada por 80 con dos saltos; (4) el intento bloqueado con la regla y su contador. Añade qué contenedor no vio cada paquete y por qué crees que fue.

    asur-lab check b3-rutas comprueba cuatro cosas: que el flujo interno tenga saltos de los tres contenedores, que exista traducción de origen en el router, que el flujo hacia el destino autorizado también esté traducido y que el intento al puerto cerrado aparezca como bloqueado con la regla que lo cortó. No publica los valores esperados: señala qué paso revisar.

    Calificación. Los criterios y los pesos de esta actividad están por definir: los decide el docente. Esta guía fija qué se entrega y qué comprueba el verificador; no fija niveles ni porcentajes.
