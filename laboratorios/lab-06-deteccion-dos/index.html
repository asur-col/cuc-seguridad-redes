Laboratorio 6: Detección y mitigación de tráfico anómalo (DoS/DDoS)

Detecta con Suricata y mitiga con nftables un SYN flood, un HTTP flood y un ataque multi-origen, en contenedores dentro de tu VM.

👨‍🏫 Docente: Ing. Rodolfo Cañas Cervantes🏛️ Universidad de la Costa (CUC)📅 Semana 13 · Formativa · ~90 min · 2026-2

Objetivo: detectar y mitigar un ataque de denegación de servicio (SYN flood, HTTP flood y multi-origen) sobre un servidor web, usando únicamente contenedores Docker en redes internas (sin puertos publicados, sin Internet en tiempo de ejecución). El estudiante escribe las reglas de detección (Suricata) y mitigación (nftables) y verifica que el tráfico legítimo siga funcionando.

Duración aproximada: 90 minutos. Entrega: ./lab evidencia genera evidencia.tar.gz para subir por Teams.

Marco ético (Ley 1273 de 2009, Colombia): este laboratorio se ejecuta exclusivamente sobre entornos propios y autorizados. El contenedor generador solo reproduce capturas pregrabadas contra el servidor del propio laboratorio (10.30.0.10, red Docker interna). Destino, tasas y duración están fijados en el código; no es configurable por el estudiante y no se entregan herramientas para atacar sistemas de terceros.
0

Antes de empezar

Trabaja dentro de tu VM de Ubuntu (por consola, SSH o escritorio en el navegador). Si aún no tienes el cliente asur-lab, instálalo una sola vez:

curl -fsSL https://asur-col.github.io/cuc-seguridad-redes/laboratorios/instalar-asur-lab.sh | bash
export PATH="$HOME/.local/bin:$PATH"

Luego descarga y levanta el laboratorio, y entra a su carpeta:

asur-lab iniciar lab06
cd ~/labs/lab06

Comandos disponibles: ./lab up, ./lab down, ./lab reset, ./lab estado, ./lab base, ./lab ataque <syn|http|multi>, ./lab recargar, ./lab check, ./lab shell <c>, ./lab evidencia.

1

Línea base (15 min)

Herramientas: ss · tcpdump · logs nginx

Mida el tráfico legítimo antes de escribir cualquier regla de mitigación:

$ ./lab base 30
[INFO]   midiendo la línea base durante 30 s (no lances ataques)
[OK]     escrito ~/labs/lab06/evidencia/linea-base.txt
  pps=22 · SYN-RECV=0 · orígenes=3

El archivo evidencia/linea-base.txt registra pps, SYN-RECV y orígenes únicos (objetivo 1 del ./lab check). Valores razonables para el tráfico normal del lab: pps entre 3 y 60, SYN-RECV entre 0 y 50, 1–5 orígenes.

2

Análisis de capturas (20 min)

Herramientas: tshark sobre datos/*.pcap

Copie la plantilla y complétela con tshark sobre los pcap de datos/ (dentro del contenedor fw o del generador):

$ ./lab shell fw
# tcpdump -q -n -r /datos/syn-flood.pcap | head -3
<encabezados de los primeros paquetes>
# tshark -r /datos/syn-flood.pcap -T fields -e ip.src | sort -u | wc -l
<conteo>

Complete evidencia/analisis-pcap.txt con sus propios hallazgos (objetivo 2) — estos valores los mide usted con tshark, no se copian:

  • flag_dominante= — qué bandera TCP domina el flood (mídala con tshark -e tcp.flags).
  • origenes_syn= — cuántas direcciones IP originan el SYN flood (-e ip.src | sort -u | wc -l).
  • tasa_syn_pps= — tasa aproximada medida con tshark (-e frame.time_relative para el intervalo).
  • http_flood= — qué tipo de petición HTTP envía el http-flood (-e http.request.method).
  • diferencia= — por qué el SYN flood satura el servidor sin completar el three-way handshake (medio saludo).
3

Detección (20 min)

Herramientas: 2 reglas Suricata con threshold

Edite reglas/lab.rules. Escriba dos reglas con threshold (umbral por origen). La plantilla deja huecos N y M para que usted los ajuste (ejemplo sin resolver):

alert tcp any any -> any 80 (msg:"SYN flood"; flags:S;
  threshold: type threshold, track by_src, count N, seconds M; sid:1000001; rev:1;)
alert tcp any any -> any 80 (msg:"HTTP flood"; flags:PA; content:"GET "; depth:4;
  threshold: type threshold, track by_src, count N, seconds M; sid:1000002; rev:1;)

Luego ./lab recargar y lance ./lab ataque syn y ./lab ataque http. Verifique alertas en ./lab shell ids → tail /var/log/suricata/eve.json (objetivos 3 y 4).

4

Mitigación (20 min)

Herramientas: nftables: rate limit, connlimit, set dinámico

Edite reglas/nftables.fw (base vacía incluida) y aplíquelo con ./lab recargar. Conceptos a explicar (sin entregar el archivo resuelto):

  • Límite de tasa SYN por IP: limit rate sobre tcp flags syn — evita que una sola origine saturen el servidor.
  • Límite de conexiones simultáneas: ct count over N por IP de origen — protege contra muchas conexiones pendientes.
  • Set dinámico con timeout (bono): bloquea temporalmente el origen que supera el umbral con update @set { ip saddr } y flags dynamic,timeout.
  • SYN cookies y limit_req de nginx: en el servidor web, no en el firewall.
¿Por qué un límite fijo no basta? Un DDoS volumétrico real satura el enlace antes de llegar al firewall; allí se necesita el ISP, CDN o scrubbing. Umbrales muy bajos generan falsos positivos contra usuarios legítimos.
Puente al Lab 7: los umbrales fijos son difíciles de ajustar; la IA (NDR con ML) aprende la línea base y detecta anomalías sin reglas escritas a mano.
5

6

Reflexión (5 min)

¿Por qué no basta este lab frente a un DDoS volumétrico real? ¿Dónde fijar los umbrales sin bloquear usuarios legítimos? ¿Cómo ayudaría la IA (puente al Lab 7)? Responda por escrito y agréguelo al final de evidencia/analisis-pcap.txt.

·

Si algo falla

  • Contenedor no arranca: ./lab estado y revise los logs del contenedor con docker logs lab06-fw.
  • Suricata no alerta: revise que reglas/lab.rules tenga sid único y threshold, y ejecute ./lab recargar.
  • El ataque llega al servidor: añada el límite de tasa SYN por IP en reglas/nftables.fw y ./lab recargar.
  • El cliente legítimo cae: sus reglas son demasiado estrictas; relaje el umbral y vuelva a ./lab recargar.
  • Docker ≥ 29 en el servidor docente: ./lab up intenta aplicar automáticamente el arreglo de enrutamiento del bridge (DOCKER-USER); en las VM del aula (Docker 28) no es necesario.
·

Entrega

Ejecute ./lab evidencia para generar evidencia.tar.gz con evidencia/linea-base.txt, evidencia/analisis-pcap.txt y las últimas líneas de eve.json y del log de nginx. Suba el archivo por Teams junto con una captura del ./lab check con su resultado.

Objetivo 6 en revisión: si tu ataque queda contenido y solo falla el objetivo 6 («muy pocas peticiones del cliente»), el resultado 5/6 es válido por ahora.
